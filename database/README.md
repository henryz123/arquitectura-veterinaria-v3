# Base de datos

`demo/seed-client-synthetic.psql` es un fixture local, transaccional e idempotente de dos cuentas CLIENT activas —una por tenant— para pruebas de navegador. Requiere las cuatro variables sintéticas locales `AV_DEMO_CLIENT_AURORA_EMAIL`, `AV_DEMO_CLIENT_AURORA_PASSWORD`, `AV_DEMO_CLIENT_BOSQUE_EMAIL` y `AV_DEMO_CLIENT_BOSQUE_PASSWORD`; no contiene sus valores. Ejecútelo solo mediante `scripts/invoke-client-synthetic-seed.ps1`, que exige `av_schema_owner`, `localhost`/loopback en el puerto 5432, la base exclusiva `arquitectura_veterinaria` y correos `.invalid`; reutiliza las funciones de registro/verificación y revierte todo el fixture si ocurre un error.

`demo/seed-groomer-synthetic.psql` crea o conserva una única cuenta STAFF sintética `GROOMING` de Aurora para recorridos B03. Requiere `AV_DEMO_AURORA_PASSWORD`, `AV_DEMO_GROOMER_AURORA_EMAIL` y `AV_DEMO_GROOMER_AURORA_PASSWORD`, valida dominio `.invalid` y política de contraseña, usa exclusivamente `av_app` contra `arquitectura_veterinaria` y ejecuta la invitación/aceptación auditadas dentro de una transacción. El invocador controlado es `scripts/invoke-groomer-synthetic-seed.ps1`; no modifica migraciones ni imprime valores sensibles.

`demo/seed-cashier-synthetic.psql` crea o conserva una única cuenta STAFF sintética `CAJERO` de Aurora para recorridos B04. Requiere `AV_DEMO_AURORA_PASSWORD`, `AV_DEMO_CASHIER_AURORA_EMAIL` y `AV_DEMO_CASHIER_AURORA_PASSWORD`. Solo acepta correo `.invalid` y contraseña local con 12–72 caracteres, mayúscula ASCII, minúscula ASCII y dígito. Usa exclusivamente `av_app` contra `arquitectura_veterinaria`, autentica temporalmente al administrador sintético de Aurora, invita y acepta el rol exclusivo `CAJERO` dentro de una transacción y revoca la sesión temporal. Si el correo ya corresponde a una cuenta que no es activa con ese único rol, aborta sin modificarla. El invocador es `scripts/invoke-cashier-synthetic-seed.ps1`; no modifica migraciones ni imprime valores sensibles.

`migration/` es la \u00fanica fuente de esquema y se copia a `backend/target/classes/db/migration` durante la compilaci\u00f3n. Flyway nunca lee migraciones desde una segunda carpeta.

`demo/seed-synthetic.psql` no es una migraci\u00f3n ni debe ejecutarse en producci\u00f3n. Ejecútelo únicamente mediante `scripts/invoke-base-synthetic-seed.ps1`: el lanzador exige `av_schema_owner`, una conexión loopback al puerto 5432 de `arquitectura_veterinaria` y contraseñas sintéticas locales fuera de Git. El SQL vuelve a rechazar cualquier base, rol o conexión no local antes de escribir. Crea exactamente dos organizaciones ficticias y permite demostrar que el mismo correo puede pertenecer a tenants distintos; no guarda ni muestra contraseñas.

G4-I00 verific\u00f3 este flujo en una base exclusiva con `av_schema_owner` como propietario y `av_app` como rol de runtime sin privilegios administrativos ni `BYPASSRLS`. La reproducci\u00f3n interactiva, sin secretos en archivos, est\u00e1 en `docs/runbooks/G4-I00_ENTORNO_LOCAL.md`.
